# Improve the whole Keller workflow

Use this skill when maintaining the client's knowledge environment, investigating repeated quoting failures, proposing a reusable skill or tool change, or running scheduled improvement work. Do not reduce the problem to retrieval weights. Start with the existing [decision-quality contract](../../../docs/decision-quality.md), [trajectory method](../../../docs/mcp-trajectory-analysis.md), and [integrated operator guide](../../../docs/keller-learning-environment.md). This is an operator skill, not a quote-worker instruction or authority to expose targets.

## Run one bounded improvement cycle

1. Inspect the previous sealed run and pending work first. Choose one observed failure mechanism that affects usable quote completion or pricing. Record the evidence, expected change and unchanged acceptance criteria before editing. Missing runtime capabilities, source availability, intake attributes, source compatibility, arithmetic, retrieval, tool failures, workflow identity and handoff are separate mechanisms; an error metric alone proves none of their causes.
2. Verify the environment with `node scripts/bootstrap-keller.mjs` and `node scripts/keller-environment.mjs verify`. Use an explicit private environment root outside Git for feedback, records and reports. Capture actual human outcomes through `scripts/keller-feedback.mjs`; preserve request/draft hashes, stable line IDs, corrections, holds, invalid requests, failures and timeouts. These operator assertions are not independent grading or automatic knowledge. Historical register prices and independently verified customer-PDF prices are different populations; never pool them or silently switch the price basis.
3. Freeze a diagnostic plan through `scripts/keller-improvement.mjs freeze`, including the existing compatible baseline, exact inputs, source/lock/skill hashes and a hard runtime budget. Run that job through `run`; reuse only validated journal artifacts. A changed code/skill fingerprint requires a new experiment, even when an old draft receipt is intact. A failure stays recorded; do not clean it up into a success.
4. Read the private case diagnostics and every pass-to-fail criterion transition. Check signed errors and variance across actual proposals, retain held/missing/invalid attempts, and corroborate a failure cause against observed tool responses or source evidence before changing the workflow. Use existing sealed MCP trajectory analysis for model-driven sessions; do not manufacture internal reasoning from a final answer.
5. Draft at most ten reusable knowledge candidates from corroborated observations or explicit operator teaching. Agent narrative, answers, oracle prices, experiment outcomes, credentials and customer-specific case solutions are not reusable knowledge. Give the unchanged batch to exactly one independent reviewer without transcript or write access. Journal malformed, missing, duplicate, conflicting or failed review as rejection; do not retry a failed reviewer or shop for a verdict. Zero accepted items is valid.
6. Stage and review candidates with `scripts/keller-knowledge.mjs`. Acceptance does not activate a record. Independently verify the cited source bytes, resolve duplicates and conflicting scope, then test a versioned skill/tool/knowledge proposal on matched development cases. Activation requires a named operator attestation binding development and separate confirmation artifacts; this records an operator assertion, not authenticated human identity or software-proved accuracy. Never write global personal memory from client-learning packets.
7. Confirm the improvement on cases preselected before the change and not consumed by development, with unchanged criteria and independent grading. An exposed fixed set or reused diagnostic split cannot become fresh confirmation. Keep the live completed-quote gate separate from historical ±20% replay and synthetic workflow checks. Require named human review before any customer release, even when an accuracy target is met.

## Keep work schedulable and finite

Use `buildSchedule` to turn observed failures into dependency-bound work items, with stable IDs and a finite attempt budget. Evidence remediation precedes a knowledge/skill candidate; measured development precedes independent confirmation. Stop a blocked item with its specific missing input instead of launching another parameter sweep. Resume verified completed stages; never replay external effects or failed knowledge reviews implicitly.

For a scheduled engineering run, use the single prompt in [the schedule contract](../../../docs/keller-learning-schedule.md). Start disabled, test one invocation, inspect its actual checkout/context and saved result, then activate only within the owner's authorized scope. This schedule improves and validates the software; it is not the client RFQ inbox scheduler. Never read production credentials into reports, write Polygres/FabriTRAK, refresh source extracts, spend on model providers, merge, activate client quote delivery, or promote business knowledge by implication.
