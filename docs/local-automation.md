# Keller local quote drafts: 15-minute operator setup

This repository can price a local request **offline** and write a draft for manual review. It does not fetch customer requests, send quotes, modify FabriTRAK, or install a background service. A client or Opulent host must supply an approved request to the inbox and poll the draft/receipt; a human must review every draft before external delivery.

For the **complete order-proposal** schema, see [pricing evaluations and orders](pricing-evals-and-orders.md). The inbox dispatches `OrderRequest` inputs to the offline order builder, preserving explicit unit prices, cost-plus inputs and supported costing worksheets. It requires line identities, order/date/customer identity and explicit shipping/tax; unknown prices or charges produce a `BLOCKED` order with a null total, not a zero-dollar priced quote. A receipt means a review artifact exists, not that it is complete or approved. Older `EstimateRequest` inputs remain supported for historical comparison only; their receipts do not certify complete costing or margin. Order-specific fields in an incomplete request are validated as an order, never silently discarded by the legacy estimator.

`quotes.csv` contains historical internal calculations, not verified customer-letter prices. The [document-evidence workflow](document-evidence.md) produces a separate, conservative customer-price register from locally transcribed and reconciled PDFs. Pass that file explicitly as `--register` to use it; do not overwrite the frozen register or silently switch a running scheduler. The existing receipt pins the chosen register's exact bytes, and document-backed analogs retain their source references for review.

## 0–5 minutes: install and check

Install Node 24 or newer on Windows, macOS, or Linux. In a checkout containing `quotes.csv`, run:

```sh
cd estimator
npm ci
cd ..
node scripts/keller-local.mjs onboard --workspace .keller-local --register quotes.csv
```

The last command exercises `estimator/examples/request.json` with `--offline` and creates `inbox/`, `drafts/`, `receipts/`, and `held/` under the chosen workspace. `LOCAL_READY` means Node, the register, dependencies, and a fully priced deterministic fixture work. `runtime_persistence` and `scheduler_workspace_binding` remain `UNVERIFIED`: the local check cannot establish that a scheduled/host run opens the same durable workspace. `INTEGRATION_BLOCKED` means the DB URL or gateway key is absent. `INTEGRATION_UNVERIFIED` only means both are configured: it does **not** certify that either external service works. Neither external credential is needed for local quote drafts. On Windows, use the same Node command with PowerShell path separators (`node .\scripts\keller-local.mjs ...`); quote any path containing spaces.

## 5–10 minutes: one safe cycle

Write a request JSON file atomically into `.keller-local/inbox/` using the estimator request schema in `estimator/README.md`. A host should write to a temporary name outside the `*.json` scan, then rename to `request-name.json`; never edit a scanned file in place. For a local fixture:

```sh
cp estimator/examples/request.json .keller-local/inbox/example.json
node scripts/keller-local.mjs cycle --workspace .keller-local --register quotes.csv
```

On Windows, use `Copy-Item estimator\examples\request.json .keller-local\inbox\example.json` and the same `node .\scripts\keller-local.mjs cycle ...` command. `cycle` forces offline execution even if a gateway key is present and starts its TypeScript runner with the current Node executable, rather than a Unix-only shim. It computes `input_sha256` from the exact request bytes and `register_sha256` from the current register bytes; the durable job key is SHA-256 of `keller-job-v1\n<input_sha256>\n<register_sha256>`. It writes `drafts/<job-key>.json`, `proofs/<job-key>.json`, and `receipts/<job-key>.json` with `DRAFT_REQUIRES_MANUAL_REVIEW`. The proof pins the draft SHA-256, both source digests, and the job key. A repeated cycle reuses the draft only after checking its proof, receipt, offline mode, and request agreement. A stopped process can restore a missing receipt only when a matching proof verifies the intact draft. A changed register produces a **new** draft under a new key, preserving prior drafts for historical review instead of silently repricing or overwriting them. Editing the request bytes also creates a new key. Inbox files remain untouched, and no draft is sent automatically.

Order requests use the distinct key prefix `keller-order-job-v1` instead of `keller-job-v1`, with the same input/register hash construction. This prevents reuse of old legacy artifacts for costed requests. Order retries verify the offline provenance, register hash, review requirement and request identity before recovering a receipt. Inspect `draft.state` and `draft.blockers`: `BLOCKED` needs follow-up, while `PRICED_REQUIRES_REVIEW` still requires named human approval. No mailbox or PDF-to-request extraction is implied by this JSON handoff.

## 10–15 minutes: connect a scheduler and review owner

Configure **one** machine-local OS scheduler to invoke that exact `cycle` command with absolute checkout/workspace/register paths, from the repository working directory. Use an account that can read `quotes.csv` and write its private workspace; supply Node's absolute executable path if scheduled sessions lack your interactive `PATH`. On Windows, create a Task Scheduler task triggered at logon and repeated at your chosen interval; on macOS, a user launchd agent can run it with `StartInterval`; on Linux, a user systemd timer can call a oneshot service with `OnUnitActiveSec`. Run the command once manually before enabling the schedule, then restart the OS/task and verify an unchanged inbox produces a duplicate, not a second draft. The scheduler is optional until a request producer and manual reviewer have been named; no request-arrival integration is bundled here.

The default `.keller-local/` is private and gitignored (as is the root `out/` export directory), but a checkout in an ephemeral Opulent run can disappear between invocations. For any such run, **configure a persistent, client-private absolute `--workspace` path** mounted into every invocation, including its `inbox/`, `drafts/`, `proofs/`, `receipts/`, `held/`, and `claims/` subdirectories. A repo-private durable volume is suitable; a Drive-backed runtime location requires explicit owner approval and data-access policy. Do not commit those artifacts or assume a sandbox-local path survives. Verify the host/scheduler as that client owner: submit a fixture, run a cycle, restart with a fresh runner bound to the same persistent path, and confirm the same job key is a duplicate with its receipt, proof, and draft intact. `LOCAL_READY` alone never establishes this scheduler+workspace binding proof.

The host should poll `receipts/<job-key>.json` and verify its input/register digests and `draft_sha256` against the referenced `draft_file` before reading it. `drafts/` contains estimates, not transmission instructions. Route a priced draft to a named human for scope, material, quantity, staleness, warnings, and confidence review; low confidence or missing usable prices require manual pricing. Only the existing human-approved delivery channel may send it. Do not let a host poll `drafts/` and auto-send its content.

Before connecting an Opulent host, the client owner must verify its intended owner, workspace, repository checkout, and persistent private runtime directory. A project automation registration alone does not prove those bindings or attach client data; do not treat registration as runtime readiness. Use a verified workspace-bound host run only after its trigger actually opens that checkout, can execute the local check and cycle there, and sees the same receipts after a fresh run. Until then, the OS-local scheduler and human reviewer are the runnable boundary.

### Optional native Opulent host binding (disabled until proven)

Do not use project-level automation registration for this job: it can pick a default workspace instead of the intended client workspace. The supported native route requires a dedicated thread created with `workspace_manage` `{ "action": "create_thread", "workspaceId": "<owner-approved-private-workspace>", "title": "<client-job-name>" }`. It returns a `threadId`; verify that thread's owner and workspace **from read-only host observations**, then save the observed binding in a private config file in the persistent client runtime. Export the proposed disabled automation with `node scripts/export-host-automation.mjs <private-config.json>`. That command makes no host calls or external writes, refuses owner/workspace/repo mismatches, and embeds [the canonical scheduled-job prompt](host-automation-prompt.md) unchanged except for the approved private bindings. Its output is a proposal marked `HOST_EXPORT_ONLY_LIVE_UNVERIFIED`, not a registration receipt.

The private JSON must name `name`, `owner_user_id`, `workspace_id`, `observed_thread` (`thread_id`, `owner_user_id`, `workspace_id`), `repository: "OpulentiaAI/keller-quotes"`, `ref: "main"`, absolute `runtime_workspace` and `register_path`, and an owner-approved named-zone daily `recurrence`. For example, the recurrence **shape** is `DTSTART;TZID=America/New_York:20261015T090000\nRRULE:FREQ=DAILY;BYHOUR=9;BYMINUTE=0`; the operator chooses the real zone/start/cadence. The exporter validates the IANA zone and agreement between the anchor and daily hour/minute, but only the live host schema can validate DST edge cases. Do not convert local time to a fixed UTC cron. Never commit this file or an export containing client IDs; keep both under an approved private runtime path.

Before any live create, inspect `automation_manage` with `{ "action": "schemas", "event_type": "schedule:recurring", "action_type": "message_session" }`, then validate the export against the live schema. The generated create payload is `enabled: false`, with one `schedule:recurring` trigger (`conditions.any[0].all[0]` is an `rrule`/`recurrence` condition), `replies: []`, and one `message_session` action whose `target_session_id` is the verified `threadId`; never use `auto_create`, `target_thread_id`, or a default workspace. Inspect the saved record before any activation. A trigger/run is an effect, not a read-only check, so activation still requires the owner-approved live context and a fresh-run persistence test. The scheduled prompt rechecks permitted **read-only** host/capability observations on every run, writes a private capability receipt, and continues on the next day only when that fresh proof matches the saved owner choices; it does not require daily manual timestamp edits. Expired auth or ambiguous identity holds and escalates. This metadata refresh authorizes neither source re-extraction nor paid preflights. These host steps have not been run from this repo and remain live-unverified.

Each actual scheduled invocation must obtain a **new, successful authenticated read-only** host observation before touching the inbox. It should contain `owner_user_id`, `workspace_id`, `thread_id`, `repository`, `ref`, `runtime_workspace`, `register_path`, `checkout_sha` (40 hex characters), `source_tool`, `read_only: true`, `observed_at` (current ISO time), and `authenticated_read: {status: "success", source_tool, action, result_sha256}`. Derive the probe status and SHA-256 digest from the actual successful read-only host tool result, not from an assumed credential-expiry date or yesterday's receipt. Discover the supported workspace/thread identity and checkout read schemas; if the tool fails or cannot establish identity, stop. If an actual provider response supplies `auth_valid_until`, include it so a reported expiry can be rejected; otherwise omit it. Store the observation privately and run `node scripts/verify-host-capability.mjs <persistent-private-config.json> <fresh-private-observation.json>`. It checks identity against saved owner choices, observation freshness (five minutes), successful read evidence, any **optional provider-reported** expiry, mount/register existence, and prior binding; only then does it write `capabilities/latest.json`. This receipt's `observation_fresh_until` is a local observation window, **not** a credential validity claim. A later run with the same approved config and a new successful observation renews it automatically. Missing/failed read proof, drift, or an explicitly expired provider credential exits nonzero without replacing the last receipt. The offline validator checks supplied evidence but cannot authenticate the host tool itself; the live tool call and schema remain an activation gate.

If a request is invalid, `held/<job-key>.json` records `HELD_INVALID_REQUEST`; correct the source request (new bytes/new key) and rerun. Identical invalid bytes remain held instead of looping. A corrupt or orphaned draft/proof/receipt records `HELD_AMBIGUOUS_ARTIFACT`; quarantine it for operator reconciliation rather than trusting or overwriting it, then resubmit an explicitly revised request once resolved. Parallel cycles use an atomic job claim, and `cycle.claimed` means another process owns or may own it, not a duplicate. Only a claim from a **proven-dead process on the same host** is reclaimed automatically; an old claim from a live process, another host, or an unknown owner remains busy for operator reconciliation. Age alone never steals a claim. Workers remove only claims carrying their own random owner token. A transient estimator/runtime failure appears in `cycle.failed`, exits nonzero, writes no receipt, and is retried on the next scheduled cycle; investigate repeated failures before delivery. Preserve drafts, proofs, receipts, and claim state across restarts. Treat requests and quotes as customer data: keep the workspace access-controlled and out of Git (`.keller-local/` is ignored).

The [single canonical host prompt](host-automation-prompt.md) is read directly by `scripts/export-host-automation.mjs`; do not maintain a second copy inside an automation UI. The owner/host chooses the approved request source and writes it atomically to the inbox. The prompt handles capability renewal, the local cycle, held/failed branches, and manual review without sending a quote.

DB refresh is separate from the offline quote worker. Only an operator with an approved source extract should run `scripts/load.py` against a disposable or authorized direct PostgreSQL endpoint; embeddings require separate authorized model access. The CSV worker does not query Polygres. The brand overlay in `brand/ckeller/au-host` is not a host integration or runnable scheduler.
