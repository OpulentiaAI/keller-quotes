# Bounded Keller improvement scheduling

Schedule engineering learning separately from the client quote inbox. The learning job may inspect source-controlled procedures, run offline diagnostics, and prepare reviewed software/skill changes. It does not ingest client RFQs, approve prices, send quotes, update production databases or activate the client's delivery scheduler.

Configure one initially disabled daily schedule with an explicit IANA timezone and the `Keller continuous improvement` prompt below. Pin the checkout, use GPT-6.1 Sol max/fast for engineering agents, cap invocations at one per day, serialize work through the controller's claim, and run one test invocation before enabling it. Read the saved record and its actual run result. Do not treat a manual trigger as proof of future cron delivery or a fresh sandbox as proof of a persistent client mount.

## Canonical run prompt

Read `.agents/skills/keller-continuous-improvement/SKILL.md` and its linked contracts from the actual Keller checkout. Inspect the current branch/PR state before changing anything. Never push a merged/closed branch, merge, enable auto-merge, or overwrite another run's active work. All host engineering subagents use `openai/gpt-6.1-sol`, reasoning `max`, fast enabled.

Run `node scripts/bootstrap-keller.mjs` and `node scripts/keller-environment.mjs verify`. Use owner-private storage outside the repository for diagnostic artifacts. Run the real frozen offline replay and unchanged comparison contract; the public fixed sample is diagnostic only. If an existing compatible baseline is unavailable, generate a current baseline with the real runner, retain it as baseline establishment and do not claim an improvement comparison. Freeze inputs/code/locks/skills before running a candidate. Use `scripts/keller-improvement.mjs` for subsequent candidate execution, duplicate verification, failure retention, per-case diagnosis and the bounded work queue.

Within one run, take at most one evidence-backed work item and one candidate experiment; use at most two writing subagents on disjoint files. No model-provider calls, production database writes, source re-extraction, customer delivery or paid retrieval are authorized by this engineering schedule. Preserve all attempts and unchanged ±20% replay criteria. Check pass-to-fail criteria and numerical variance, not just aggregate scores. Missing evidence or independent confirmation is a blocked item with the exact need, never permission to label a reused diagnostic split blind.

Create at most ten scoped learning candidates from corroborated source observations or explicit human feedback. Use exactly one independent batch reviewer, no transcript/write access, strict uppercase verdicts, and terminal failure handling. Do not auto-activate accepted knowledge or global memory. Version a proposed skill/tool change, verify it locally and on matched development, and request independently labeled untouched confirmation when the release contract needs it. An operator attestation is not authenticated human identity or proved live accuracy.

Stop after the bounded milestone: persist the diagnostic/work-item state, verify any software change and open a PR without merging. Report the actual source hashes, completion/hold/error denominators, criterion losses, regression status and remaining input need privately. Share only public-safe summaries on GitHub. If the separate live, independently reviewed completed-quote gate exceeds 90%, report its denominator and evidence, then switch to regression/maintenance work; do not silently widen quote-release permission. Otherwise record the highest-priority next item, without claiming that a scheduled run itself achieved the goal.
